# 验收：怎么知道自己没在自欺

## 采集阶段

| 检查 | 通过标准 | 常见造假 |
|---|---|---|
| 容器找对了 | 滚动后 `scrollHeight` 增长，或卡片数变多 | 滚了 window，页面没动还以为在加载 |
| 字段解析对了 | 抽样 10 条，作者非空率 >80%，描述非空 | author 全空却继续往下跑 |
| 去重有效 | 总数 < 滚动轮次 × 单轮卡片数 | 每轮重复计一遍，抓出 3000 条幻觉 |
| 到底判定 | 连续 3 轮无新增 | 滚 3 次就停，实际只到 1/10 |
| 覆盖率算过 | 已抓 / 页面总数，写成百分比 | 只说"抓了一些" |

## 分类阶段

| 检查 | 通过标准 |
|---|---|
| 命中率合理 | 高相关主题命中率 30%–60%；接近 100% 说明关键词太宽，接近 0 说明表错了 |
| 抽样人眼核 | 每类抽 5 条，标题是否真属于该类 |
| 未命中也被看 | 未命中条目里有没有该进类但漏了的 |

**关键词表最常见的病是"太宽"**：`工具`、`模型`、`运营` 这类词会吃掉一切，让每类都虚高。宁可窄，不要宽——窄了漏，宽了假。

**打标结果对词表极度敏感，所以结论必须报口径。** 同一批 718 条样本，我们自己实测过两版词表：

| 词表版本 | 命中（去重） | 名义时长 |
|---|---|---|
| 窄表（不收泛词） | 326（224） | 75 小时 |
| 宽表（补入 `增长`/`团队`/`品牌` 等） | 399（268） | 89 小时 |

**差 44 条、14 小时。** 这个差异不是错，是口径。所以交付里要写清：多少条样本、什么词表、命中多少——否则对方拿你的数去比别人的数，一定对不上。

迭代方法：`python3 scripts/classify.py in.json --show-unmatched 10`，看未命中里有没有明显该进类的，有就补词，再跑一次。通常两三轮就收敛。

## 盘查阶段

| 检查 | 通过标准 |
|---|---|
| 时间账算过 | 有明确"多少条 × 多少分钟 = 多少小时" |
| 砍到 7 条 | 不是 20 条也不是 3 条 |
| 每条有产物 | 排期表里每行都有"当天产出什么" |
| 盲区 ≥3 行 | 且每行说明代价 |
| 区分三类信息 | 事实 / 经验建议 / 待核验，分开写 |

## 验证阶段

引用任何外部条目都必须**打开过**：

- 视频：打开详情页，记赞/评/藏、发布时间
- 仓库：核实星数、许可证、能否下载解包
- 数字：**列表页数字一律回详情页复核**

做不到的写"未定位"、"未核实"，**不写"应该没问题"**。

## 交付前的最后三问

1. 这份清单里，有几条我**实际打开过**？（必须是全部）
2. 我引用的数字，有几个是**列表页缓存值**？（应该是 0）
3. 如果使用者照着做，第 3 天会不会因为"学不完"而放弃？（会 → 砍量）

## 禁止出现在交付里的表述

- "已全部抓取"（除非覆盖率 100%）
- "该仓库已开源"（除非你打开过仓库页）
- "效果很好"（除非有实测数据）
- "建议学习"（没有砍量标准的建议等于没建议）
